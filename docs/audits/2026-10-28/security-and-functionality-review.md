**Security and functionality review — 28 October 2026**

Reviewed local main at `ca2ceb2fa09b5b1bad86fb7011bb5880decc0a7c`, using the running application at `http://127.0.0.1:8000`. This is an assessment, with no application fixes applied. Findings concern this checkout and local configuration; the Cloudflare tunnel and production infrastructure were not tested.

The application has confirmed file-disclosure and privacy vulnerabilities, plus a seller-ownership failure reproduced with synthetic accounts. Address the security and accounting findings before treating this deployment as ready for public use.

**Evidence and scope**

- Browser checks covered 14 live guest pages and 13 authenticated server-rendered snapshots across buyer, seller, admin and logistics. The snapshots were generated through Laravel with existing role accounts, array sessions, and a database query guard that rejected writes. They test rendering and JavaScript, not a complete authenticated browser session or every action.
- Browser form submissions and fetch/XHR requests were blocked. Some logistics polling/address requests were consequently not exercised. The buyer profile GET attempted an implicit address update; the guard stopped it. That is an assessment limitation, not evidence that the real profile page returns HTTP 500.
- Public API GETs checked product serialization, pagination and vehicle types. Only field names were retained from private user attributes. The file-disclosure proof used the non-secret `composer.json`; no credentials or identity documents were retrieved.
- Existing isolated tests: **45 passed, 1,009 assertions**. These cover shopping, ownership checks, cancellation, refunds, payouts and structural checks within their fixtures.
- Three temporary audit cases in SQLite memory confirmed cross-store remittance confirmation, swallowed ledger failures, and token issuance to an unverified account: **3 passed, 11 assertions**. Their assertions demonstrate the faulty behavior; they are not evidence that these controls are secure. Temporary fixtures/helpers were removed after assessment.
- Read-only Composer and npm advisory checks completed. No dependency installation or automatic fix was run.
- No application source/configuration, migrations, account records, orders or financial records were changed. Ordinary HTTP requests can produce normal sessions and logs. The only retained additions are this report and sanitized browser results.

**Security findings, in recommended repair order**

| ID / priority | Finding and evidence | Required work |
| --- | --- | --- |
| SEC-01 — Critical | **Unauthenticated file disclosure.** `routes/shared/storage.php` concatenates an unrestricted path onto several roots, including private `storage/app`, without canonical containment. A traversal GET returned HTTP 200 and the project `composer.json` from outside the public directory. This demonstrates arbitrary readable-file access within the server process's permissions. Credential and private-document exposure are potential consequences; those files were deliberately not fetched. | Replace the catch-all fallback with public-disk-only delivery and canonical path confinement. Serve private files through ownership/role checks. Verify encoded traversal and private-file denial. Review exposure history and rotate secrets if this route has been publicly reachable. |
| SEC-02 — High | **Public reviews expose private user fields.** An unauthenticated GET to `/api/products/4` returned `reviews[].buyer` with keys including email, phone, birthday, address fields, `id_image`, `otp` and `otp_expires_at`. No claim is made that an OTP was live/non-null. `ProductController::show()` and `StoreController::reviews()` serialize full buyer models; `User::$hidden` hides only password and remember token. Product responses also load an unrestricted Seller model when its relationship resolves. | Return explicit public API resources/allowlists. Keep OTPs and identity-document paths out of all public serialization, and audit seller serialization for tax/document data. Add response-contract privacy checks. |
| SEC-03 — High | **Seller identity collisions break store isolation.** `Remittances::sellerKeys()` accepts both a seller row ID and its user ID. Those namespaces can overlap with another seller's user ID. With synthetic accounts, seller A successfully posted to the real seller remittance-confirmation route and changed seller B's remittance to `confirmed`. No real remittance was modified. The same dual-ID convention is used in return/payout helpers and needs review. Product-to-seller relations can also resolve null or the wrong row. | Adopt one canonical seller foreign key, reconcile historical ownership, then authorize through that relationship. Cover colliding IDs in remittance, return, balance, payout, catalog and seller-data tests. Preserve real ownership during migration. |
| SEC-04 — High | **Application status is available using an email address alone.** Public logistics rider/center status API routes have no authentication or ownership proof. Rider responses include phone, license/registration details, notes and review logs. Center responses include owner names, TIN/SEC numbers, notes and document filenames. The public web center lookup also uses only email. Confirmed in route/controller review; no applicant's status was queried to retrieve private data. | Require an authenticated owner or a short-lived verification link/code tied to that application. Return a limited public status and keep internal review notes private. Rate-limit lookups. |
| SEC-05 — High | **Seller identity and tax documents are stored publicly.** `SellerApplicationController` uploads IDs, DTI certificates, BIR forms and permits to the `public` disk alongside ordinary branding assets. Seller model helpers create public URLs for these files. This remains a concern even after fixing SEC-01. No actual document was downloaded. | Move sensitive files to private storage, migrate existing files safely, and restrict previews/downloads to their owner and authorized reviewers. Keep logos public. |
| SEC-06 — High | **Several login routes lack brute-force limits.** Runtime route middleware confirms no throttle on `/login`, `/seller/login`, `/admin/login`, `/api/auth/login` or `/api/login`; their controllers also lack an equivalent attempt limiter. Registration/forgot-password entry points need abuse controls. Logistics API login already has a throttle, and logistics web login has its own limiter. Existing OTP verification attempt limits should be retained. | Apply consistent per-account/per-IP limits and recovery protections to every authentication entry point. Consider stronger authentication for administrators. No live credential guessing was performed. |
| SEC-07 — Medium | **Email verification can be bypassed through an alternate login flow.** An active synthetic user with `email_verified_at = null` received an API token from `/api/auth/login` without an OTP. The web login verification policy is therefore not enforced consistently. New seller applications also set new accounts' `email_verified_at` directly without proving email ownership in that controller. | Define one verification policy and enforce it across web, API, chat and application/account-creation entry points before granting the corresponding capabilities. |
| SEC-08 — High maintenance priority | **Unsupported framework and vulnerable dependencies.** The lockfile contains Laravel **11.57.0**. Composer reported five advisory records representing four distinct Laravel advisories: TokenGuard bypass, debug-page XSS, temporary signed-URL confusion and email-rule CRLF injection. npm reported two affected packages: Vite **5.4.21** (high aggregate severity) and esbuild **0.21.5** (moderate). Advisory applicability is conditional: the configured app uses session/Sanctum rather than the affected built-in TokenGuard, and debug is disabled. These scans do not demonstrate a current account-takeover exploit in this app. | Plan a tested upgrade to a supported, patched Laravel version and compatible build dependencies. Assess each advisory against actual enabled features. Do not expose development servers through a public tunnel. |
| SEC-09 — Medium | **Tokens lack a consistent expiry/recovery revocation policy.** Runtime Sanctum expiration is null. The shared password-reset callback changes password/remember token but does not revoke personal access tokens; no corresponding revocation listener was identified in the reviewed application source. The separate rider API reset already deletes tokens, so the gap concerns consistency across entry points. | Define token lifetimes and revoke outstanding tokens/sessions as appropriate on password reset, account compromise and sensitive account changes. Confirm behavior with isolated recovery tests. |
| SEC-10 — Medium hardening | **Browser protections need deployment work.** Sampled local responses lacked CSP, frame protection, `X-Content-Type-Options` and Referrer-Policy. The local environment has no explicit secure-session-cookie setting. Several layouts use runtime Tailwind and floating CDN script versions. HTTPS/tunnel response headers were not assessed. | Configure/test production HTTPS, proxy trust and secure cookies, then add compatible security headers. Bundle/pin dependencies and introduce a CSP that fits the current Alpine implementation. Verify on the actual deployed host. |

**Accounting and functional work**

| ID / priority | Observed problem | Required work |
| --- | --- | --- |
| FIN-01 — High | **Cash confirmation can report settlement success while accounting fails.** `Payments::recordCheckout()` and `settleForDelivery()` swallow exceptions. `Remittances::confirm()` sets `confirmed` before settlement and reports true even when the ledger write fails. An isolated injected ledger failure produced a confirmed remittance, pending/unpaid order/payment, no ledger row and no retry through repeated confirmation. | Make financial state changes atomic, propagate required failures, report accurate results and provide an idempotent retry/reconciliation path. Test checkout creation and final settlement failure independently. |
| FUN-01 — High | **Seller voucher editing submits to the wrong endpoint.** Browser inspection opened an existing voucher and found the edit form targeting `/vouchers/1`; the registered save route is `/seller/vouchers/{voucher}`. Initial page load also produced 11 Alpine null-property errors because `editing` starts null. The edit dropdown omits the supported free-shipping type. No save was submitted. | Generate the correct named route, initialize/gate edit bindings safely and preserve all supported voucher types. Verify create/edit/disable and buyer redemption together. |
| FUN-02 — High | **Vehicle-type lookup returns HTTP 500.** `/api/logistics/vehicle-types` failed live. `VehicleTypeController` uses `$t.name`, `$t.label` and `$t.capacity_kg` instead of PHP property access. | Correct the response mapping and check the rider vehicle picker against actual active types. |
| FUN-03 — Medium | **Invalid pagination causes a server error.** `/api/products?per_page=-1` returned HTTP 500. Product/store/review pagination accepts unbounded `per_page`. Large limits are a resource-consumption risk; no load test was performed. | Validate positive bounded page sizes and return a normal client validation error. Apply limits consistently. |
| FUN-04 — Low | **Center-application step labels raise a JavaScript syntax error.** The live wizard emitted `Unexpected token ')'`. The cause is an extra closing parenthesis in the step-label `:class` expression at `resources/views/logistics/center-application-apply.blade.php:224`. The wizard component still initialized at step 0; this does not establish that submission is broken. | Correct the label expression and exercise step navigation, validation and error highlighting. Full submission/email/upload handling remains untested. |
| FUN-05 — Medium | **Returns cannot reliably select a purchased variant and use the wrong time anchor.** `Buyer/Api/OrderController::requestReturn()` selects the first order line by `product_id`, so two variants of the same product are ambiguous. It measures the return window from mutable `order.updated_at`; later settlement/status writes can extend the window. Confirmed in code review. | Select and authorize an explicit order-item ID, preserve variant identity, and calculate eligibility from an immutable delivery/completion timestamp agreed for multi-parcel orders. |
| OPS-01 — Medium | **Migration history and complete test coverage need reconciliation.** There are 113 migration files; 44 filenames are absent from the current migration ledger, despite existing tables. This is not proof that 44 schema changes are missing, and running all of them blindly may conflict with existing tables. The complete MySQL suite remains unverified because the configured account cannot access the dedicated test database; most default SQLite tests also require a schema setup. | Reconcile history against schema on a backup/staging copy. Validate a clean install and upgrade path, restore isolated MySQL test access, and run integration/concurrency coverage. No migrations were executed during this review. |

**What currently works within the checks performed**

- Homepage, shop, sale, product/store browsing, help and authentication entry screens loaded in the live guest browser. No missing local CSS, JS or image responses were observed on the 27 sampled pages, with CDN access available.
- Guest requests to seller/admin/logistics dashboards redirected to login, and unauthenticated cart/orders API requests returned HTTP 401.
- Buyer cart/order history, seller dashboard/products/orders/remittances, admin dashboard/payments/account management, and logistics dashboard/deliveries/reports rendered HTTP 200 with the intended role templates in the read-only snapshot harness. Actions and live authenticated polling were not certified by these render checks.
- The passing isolated shopping tests exercise quantities, variants, stock limits, sale-aware prices, wishlist/search, voucher claims, selected checkout and foreign-cart/address rejection.
- The passing commerce tests exercise ownership of buyer order details/cart operations, seller chat isolation, idempotent refunds/returns/cancellation, payout limits/atomic approval and inactive-session rejection. SEC-03 demonstrates a separate gap in the mixed seller-ID convention that those existing tests do not cover.
- Debug is disabled; password/remember-token fields are hidden; important mutation routes use CSRF protection; logistics login and several OTP endpoints have rate limits. These controls should be preserved while fixing the gaps.

**Limits and follow-up verification**

No load/denial-of-service tests, real purchases, external bank/refund movement, credential guessing, real application submissions, mail delivery, Google OAuth completion, physical rider handoffs or production-infrastructure tests were performed. Cash-on-delivery accounting is present; bank transfers are recorded as external handoffs, not executed by this system.
