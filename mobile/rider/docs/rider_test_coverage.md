# Rider App test-case coverage matrix

## Scope and evidence

This matrix covers all 100 requested IDs in the supplied black-box workbooks:

- `BTW_Blackbox_Test_Cases_Account_Creation-Rider-1.xlsx` (`TC-RID-001`–`TC-RID-047`)
- `BTW_Blackbox_Test_Cases_Rider_Modules-1 (1).xlsx` (`RID-PROF`, `RID-AVAIL`, `RID-JOB`, `RID-PICK`, `RID-DLV`, `RID-FAIL`, and `RID-EARN`)

The short requirements below retain the workbook's test scenario wording. Statuses describe the evidence available in this Rider App repository, not a result from executing the workbooks against production services or other roles. `Covered client` means the rider-side behavior has implementation and automated client tests; it does not assert server enforcement or a complete black-box pass. `Partial` means the client behavior exists or is tested, but a required server-side effect, integration, or device check remains. `Blocked` means the required backend behavior/API is not available in this repository. `Unverified` means the case needs additional test or device evidence. `Out of rider-app scope` means the case is for the Logistics/admin or another role's application.

The Rider App repository contains API callers and client tests, not the integrated Laravel server implementation. No backend-only claim below is treated as verified. Test files listed as evidence are mocked/unit/widget tests unless explicitly stated otherwise.

## API/backend dependencies that remain

The Rider App client calls services such as `POST /rider/apply`, rider delivery/status/pickup/complete/failed endpoints, and rider remittance list/`sent` endpoints. Those callers and mocked tests do not supply the server implementation. Based on the contracts available in this repository, the following require authorized backend implementation or end-to-end verification:

- Job offer expiry, decline handling, three-decline threshold, unassigned queue, atomic assignment, active-job cap, cross-company enforcement, auto-assignment, and locked-phone push offer/countdown.
- Server-side OTP attempt limits and 15-minute lockout.
- Server-side required proof-photo validation, COD enforcement, delivery ownership/state-machine enforcement, and persisted/displayable delivery GPS.
- Automatic failed-delivery attempt counters, retry scheduling, and Return to Sender transitions/notifications.
- Rider creation/activation-email delivery, activation-link issuance/expiry/one-time use/resend, and mobile web activation. The client application service only submits `POST /rider/apply` and email-code/status operations; the deep-link service handles login and password reset, not activation.
- Server uniqueness for rider plate/license/mobile, document replacement/re-verification, suspended-rider assignment prevention, and cross-role/company isolation.
- Logistics remittance confirmation/reconciliation, shortfall flags, and authoritative COD/pay balances. The rider remittance service exposes listing and `POST /rider/remittances/{id}/sent`, not confirmation.
- Buyer/Seller/Logistics notifications and views; the rider client cannot prove those role-side effects.
- Automatic offline behavior after GPS/heartbeat inactivity and offer suppression.
- Offline pickup synchronization and deduplicated status/pay.
- Backend acceptance limit for proof photos. The Rider client validation is 5 MB; the reported backend behavior accepts 8 MB.

The integrated Laravel backend is reference-only and was not modified or treated as an authorized implementation target.

## Business-rule conflicts requiring an owner decision

These are preserved/documented, not silently resolved:

1. **Public rider registration:** Rider App supports self-registration through Apply (`POST /rider/apply`), while `TC-RID-029` requires no public rider registration. Product/security must decide whether Apply stays public, becomes invite-only, or is removed.
2. **Pickup identifier:** Rider UI verifies the assigned job's `tracking_number`, while the reported backend pickup method validates `pickup_pin`. Backend/API and product owners must agree on one identifier and provide matching request/response semantics before integration.
3. **Required proof:** Rider UI requires a proof photo, while the reported backend accepts optional proof photo/OTP. Decide and enforce required evidence consistently on both client and server; OTP requirements may vary by order type.
4. **Failed delivery policy:** Client provides failed-delivery reasons and Return to Sorting Center guidance, while the reported backend does not automatically enforce attempt limits or RTS transitions. Logistics/product must define attempt counting, refused-delivery handling, and the RTS threshold.
5. **Proof-photo size:** Client limit is 5 MB while the reported backend accepts 8 MB. Product/API owners must set one limit and align validation, compression, error messages, and server enforcement.
